# Changelog

All notable changes to agent-taskwatch are documented here. The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and this project follows [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Fixed
- Worker instructions grant precise job-folder writes for findings, repeated-rule evidence and declared public-text files consistently across work, fix and resume, without authorizing the whole folder or publication (see [configuration](docs/configuration.md)).
- A review cycle no longer allows four reviews: the first review counts toward `max_reviews` (1 to 3, default 3, optional in `jobs-config.json` and per submission, frozen at submit). A failed review starts a fix only when a later review remains, an answer without a verdict reviews again without a fix, and check repairs use the recovery budget, not the review budget (see [configuration](docs/configuration.md#recovery-and-decisions)).
- A terminal HTTP 429 of a model call no longer spends recoveries or reviews. The step ends, the saved stage waits until the evidenced `retry-after-ms` or `Retry-After` time with its execution slot released and its target kept, and one retry starts when due; without a usable hint the job stops at `user_wait/rate_limit`. Later final errors supersede an earlier 429 even on the same line, all three HTTP-date forms are accepted in UTC, and pre-epoch dates become already-due retries (see [configuration](docs/configuration.md#rate-limits)).
- Records written before review reservations decode without being rewritten. The review count is derived from the launches since the latest resume, with the stored fix rounds as a lower bound. A launch-free cycle proves zero use only before execution in the initial or explicitly resumed cycle, with no spent fix rounds; approval-only events and a previous cycle's unit awaiting release do not spend that cycle. Otherwise, unproven remaining capacity counts as used up before another model call.

### Added
- Example Hermes skill `examples/hermes/skills/taskwatch/SKILL.md` for splitting a request (`docs/review/design.md`), submitting receipt-key chains (`docs/configuration.md#chains-and-gates`), arming `needs --wait --from <cursor>`, approving gates after `taskwatch brief <predecessor>`, and relaying the delivery card unchanged (`docs/configuration.md`, "What needs the owner").
- A fixed finding of a code job names the commit that fixed it: a full SHA that is a later commit than the one the review judged and that HEAD contains, or HEAD itself for a fix of public text only. `findings.json` must be valid, with no duplicate or unknown entries (`docs/checks.md`, "Finding records and repeated rules").
- Two consecutive substantive failed reviews of a cycle that share a rule id stop the job at `user_wait/root_cause_required` before another fix or review. `resume` then needs a `root-cause.md` changed since the stop with a complete section for each rule.
- `taskwatch show [<job>]` adds a derived `activity` key (`<stage> <m>m; last progress <m>m ago: <last non-empty progress line>`, cut to one line of at most 120 characters, or without the trailing `: <line>` when the progress file has no non-empty line yet) for jobs in `work`, `fix`, `check` and `review`, and `null` for stopped or finished jobs (`taskwatch/activity.py`; `docs/configuration.md`, "What needs the owner").
- Optional `<root>/taskwatch/defaults.json` records standing owner choices (`id`, `value`, `scope` = `global` or a target path, `source` = the owner's words), validated against `docs/kinds/defaults.schema.json`. Every design job's work and review messages name the file and its short hash, the most specific matching scope wins (`global` < shorter target path < longer target path), and the `choices.json` check fails a malformed file, an unknown `defaults_applied` id, or a pick whose `id` has an applicable default (`docs/kinds/design.md`; `docs/configuration.md`, "Owner defaults").
- `predecessors` in a submission accepts an existing job's `receipt_key` as well as its id (id first, else `receipt_key`), and `base` accepts `@<receipt key>` for the branch `<branch_prefix><first 8 characters of the id>` of an existing code job, so a chain of ordered units can be submitted in one pass while the stored record keeps job ids and branch names (`docs/configuration.md`, "Chains and gates").
- Design reviews split a plan by logical change, not by size: a unit over 400 lines or 10 files and a job over 700 lines or 3 units are a signal to confirm it is still one logical change, and size alone is no finding and no decision for the owner (`docs/review/design.md`, D-10, D-11, S1).
- Round 2 and later of a code review review the fix, not the whole job again: the message holds the prior findings, the diff since the last reviewed commit with `--stat`, the last check result, the touched files and the delta ratio, and the reviewer closes each finding, reads every changed line and the users of what changed, and reads nothing else of an untouched file. taskwatch sends a full review instead when the delta is over 50% of the first diff or over 400 lines, the base commit changed, an earlier round had a P0, a security or approval-scope path changed, or a rule recurred, and has the reviewer read in full a file no earlier round saw. The review record keeps `base`, `minutes`, `new_findings` and `delta_ratio` for tuning the thresholds (`docs/checks.md`, "Re-review scope"; `docs/review/code.md`).
- Setup text for a reviewer that is not omp: one `review_command` example each for `codex exec`, `claude -p` and `gemini -p` with their read-only flags and the sources checked, how the verdict is found, and the limits of print mode, which cannot restrict the other tool's tools (`docs/configuration.md`, "Reviewer other than omp"; `docs/review-launch.md`, "Print mode limits").
- `review_mode: "print"` in `jobs-config.json` lets a reviewer that is not omp (`codex exec`, `claude -p`, `gemini -p`, any program) review a job: the command gets the message on stdin, and `{schema}` and `{output}` name the verdict JSON Schema file and a last-message file. The runner finds the verdict in plain output, a wrapper such as `claude -p --output-format json`, or the last-message file, validates it against `docs/launch/review-verdict.schema.json`, and fails the round with the schema error when it does not match. The default `rpc` is unchanged (`taskwatch/review_print.py`; `docs/launch/taskwatch-print.md`).
- `WORKFLOW.md` tells the worker to run only the tests for the files it changed while working and the whole check once, with `taskwatch check <job> --run-command`, just before it ends (`docs/configuration.md`, "Checking a result before it ends").
- A check whose result fingerprint and basis equal those of an earlier check of the job whose command exited 0 does not run the command again; it records `reused_check` and still runs the file, text and finding checks (`docs/checks.md`, "Job checks").
- A review reply with a malformed verdict line, finding line or scope is answered with one follow-up prompt in the same reviewer session (the exact errors and the contract) instead of a new review round; a second malformed reply fails the round as before. The `reviewer` key of the verdict line is optional, and the review record holds the name of the command the runner started (`docs/launch/taskwatch.md`; `docs/checks.md`, "Review records").
- `taskwatch check <job> [--run-command]` prints what the check step would reject about the shape of a result (files, checklist, brief, public text, commit messages, finding records, uncommitted changes) and exits non-zero when anything is left. The check step calls the same functions, and the End section of `WORKFLOW.md` names the command as the last step before the agent finishes (`docs/configuration.md`, "Checking a result before it ends"; `docs/checks.md`).
- A review finding line may carry a `summary`, one sentence of at most 160 characters in the owner's words; a `PASS` with a P2 or P3 finding and no `summary` is not accepted. Older records and replies without it still parse (`docs/launch/taskwatch.md`, `docs/review/common.md` C-17).
- Optional `commit_rules.bullet_one_line` in `jobs-config.json` (off by default): the commit check of a pull request unit fails a body bullet that continues on an indented line (`docs/configuration.md`, "Commit rules"; `docs/checks.md`).
- The decision brief has a sixth required heading, `## Card`: a conclusion of one or two lines that says whether the owner must decide something, then at most 6 bullets of at most 160 characters, each about one change for the user, with no `file:line` pointer. The check fails more bullets as too big a job. The delivery message is built from it (see the card entry below).
- `Changed:` in `taskwatch brief` shows the size of a code job's diff, `Changed: 12 files, +340 -120: a, b, c, d (+8 more)`, from one `git diff --numstat`; a binary file counts as a file and adds no lines.
- Design reviews judge how a plan is split into units, jobs and lanes (`docs/review/design.md`, "Splitting a plan", rules D-10 to D-18 with checks S1 to S8), and the spec template has a 13th heading, `Units`, that submit enforces like the other twelve.
- `taskwatch brief` output is at most 80 lines in all, the worker-brief path and the reply template included, and a cut says how many lines were omitted from this output (it used to point at the worker brief, which does not hold the cut text, and ran to 82 lines).
- Documentation for chains: the four job kinds and what each checks, the gate rule (`approval_required` with `predecessors` opens after every predecessor is `done`), the rule for submitting ordered units, and how the reply to a pick list reaches the next job.
- A job whose `outputs` include `claims.json` passes a source check in code before review: the saved `sources/`, a `sources/index.json` with url, date, kind and hash, and the claims with their quotes. It fails a quote that is not in its saved source (after whitespace, quote-mark and dash normalization), a claim number that is not in its quote, uncited or unknown claims, and an absence claim without search terms; claims that rest only on snippets are counted in the brief. The reviewer gets `source-table.md` and judges support only for pairs the check found present (rule S-9), and such a job always reads `source.md`.
- A design job writes `choices.json`: at most 5 picks for the owner (each with at least 2 options, evidence and a recommended option), the choices it decided itself with a source, and the existing tools it searched for. Picks are implementation choices (language, runtime, dependency manager, packages, layout, shared conventions, an existing tool); permission, deploy, publish, spending and scope stay with the approval scope and the gate. The check validates the shape and the `file:line` evidence, `brief` shows the pick list and ends with `reply: ok | <id>=<key|text> ... | free text`, and `needs` shows the short form `reply: ok | <id>=<key> | text`, and an implement job after a design job fails its check without a `PICKS:` line in its approval source that answers every pick. Rule D-9 flags an approval request in `picks`.
- `taskwatch needs` lists what waits for the owner: gates (`approval_wait`, with the predecessors' briefs and decision counts), jobs in `user_wait` (round, open findings, repeated rules), queued jobs blocked behind a cancelled or stopped predecessor, and with `--from <cursor>` the jobs that finished since. `needs --wait --from <cursor>` blocks until an item the cursor did not hold appears, so one watcher per room replaces one `watch` per job. It reads without a lock and writes nothing; see [Job records](docs/configuration.md#job-records) for storage and cursor semantics.
- `taskwatch brief <job>` prints the decision brief, composed on read: the runner's facts (kind, verdict, rounds, check result, result location, changed files, open finding counts, time), the worker's `brief.md`, the reviewer's `checked` and `not_checked`, and every finding.
- Every job with a work stage writes a decision brief, `brief.md` in its job folder: why the job ran, what changed, the choices made, the decisions the owner must make and where to look. The check fails a missing or empty heading, a file over 60 lines, a bullet without a `file:line` pointer, or a pointer to a file or line that does not exist. `WORKFLOW.md` carries the contract and the rules of the job's kind (`docs/kinds/`). The verdict line of a review needs nonempty `checked` and `not_checked`, and rule C-19 has the reviewer compare the brief with the result. P2 and P3 findings never cost a round: they are left to the owner in the brief.
- A job with `predecessors` lists each predecessor's kind label, stage, result location, result fingerprint and `brief.md` path in its work and review messages, so the result no longer has to be pasted into the prompt by hand. Nothing is copied.
- `approve --reason` appends `Gate <date>: <reason>` to the approval source instead of replacing it, so the original approval and the owner's words at the gate both reach the worker and the reviewer.
- A scan runs two seconds after a step ends and after `submit`, `approve` and `resume` (a transient `systemd-run --user` timer), so the next step no longer waits for the five-minute timer. A failed step does not wake, which keeps the timer's retry spacing. The scan records a `launched` event per step, and a suspected stall is stopped only after 300 seconds.
- Code jobs accept an optional `public_text` list of pull request units. The check fails a unit whose commit message has a subject that is not `type(scope): summary` or `type: summary`, a subject or line over 72 characters, no blank line after the subject, or a trailer line, and fails a missing `pr/<id>/title.txt` or `pr/<id>/body.md` in the job folder.
- One review covers a code job's diff and its public text. The reviewer reads a read-only snapshot of each unit's title, body and commit messages; a later text edit makes the PASS stale and starts a text-only round that shows the text diff. `taskwatch text <job> --out <dir>` writes the reviewed title and body with one `Review evidence:` line, and exits 2 when the text changed since the review, 3 when no review has passed.
- Review findings are one JSON line each (`finding`, `severity`, `category`, `rule`, `location`) with a `### F<n>` heading. After a failed review the worker records each finding in `findings.json` as `fixed` or `not_fixed`; a rule that repeats in an earlier round or in the last 10 jobs for the same target needs a `root-cause.md` section. `state/findings.jsonl` indexes the findings.
- The delivery message is the owner's card: the worker's conclusion, then only the lists that have content, `Changed` (the worker's `## Card` bullets), `Small problems left` (the `summary` of each finding of the last review) and `Not checked` (the items of `not_checked`), at most 6 bullets each and under 4096 characters. It has no paths and no pick block; the full brief, the review file and the `Public text` and `Text fingerprint` lines are at the end of `taskwatch brief`. Optional `language` in `jobs-config.json` (`en` default, `ko`) selects the three headings (`docs/configuration.md`, "Language").
- A spec for a `code` or `design` job follows `docs/spec-template.md`: submit refuses a missing or empty heading, and a bare `n/a`; `n/a: <reason>` passes. `source` and review-only jobs skip it.
- The reviewer of a `code` or `design` job answers eight design questions in the `design_check` of the verdict line, and the review message carries the approval source and scope. Guidelines: an owner decision is outside review, a writer's choice in the spec is not (C-1, K-4, C-18); K-19 compares writes outside the workspace with the approval scope.
- Code jobs start from a freshly fetched `origin/<default branch>` on a named branch (`<branch_prefix><id8>`, default `taskwatch/`), record `base`, `base_note`, `branch`, `workspace_state` and `branch_state`, and accept an optional `base` field for stacked work. The scan removes a clean worktree at `done` and `cancelled`, keeps a dirty one with the reason, and deletes the branch only once it is merged or squash merged into `origin/<default branch>`.
- Optional `env` object in `jobs-config.json` sets the environment of every process a job starts (omp worker, reviewer, check command, runner git commands); `PATH` entries expand `~`, `$HOME` and `$PATH`, so jobs find tools in `~/.local/bin` without per-job approval.
- A job keeps its checklist and progress files in its job folder instead of the worktree, and the worker prompt gives their absolute paths, so records are never committed into a result and the clean-tree check needs no exception. Records that name `.taskwatch/...` still load.
- Optional `review_command` selects a separate executor command for independent job reviews, falling back to `omp_command` when omitted.
- Review-only jobs: submit a `review_target` (files or a commit) to review it without a work stage; the parsed verdict is recorded and delivered.
- `python -m taskwatch.reviewer_launch` builds the omp reviewer command at run time from an omp agent definition and the `docs/review` guidelines, so a review started by taskwatch or by omp alone reads the same guideline text; `review_command` accepts `{guidelines}` and `{review}`.
- Standalone approved job submission, parallel timer scheduling, transient omp RPC runs, interruption recovery, command checks, capped independent review fixes, and configured result delivery from `deliver_pending` to `done` through a literal-argument command with a fixed 60 second timeout. Only confirmed sends finish; every other outcome stops for user judgment without automatic resend. The existing Hermes plugin remains available.
- `taskwatch_approve` records conversational start and apply approvals without hand-written JSON; retries return the existing approval and apply refuses a stale or dirty result.
- `scan` warns through the configured user destination when the board is unreadable and exits 1; config failures exit 1 with the file and cause on stderr for the timer journal.
- Project skeleton: documentation, CI, and issue and pull request templates.
- Review guidelines for code, design, and source-checked documents, with a slot for project rules.
- CI checks that review guidelines keep required sections, local references, and unique rule ids.
- 13 review cases and a scorer that counts missed findings, false positives, severity mismatches, and verdict agreement from a human mapping.
- Hermes plugin entry that pins the tested Hermes version.
- `hermes taskwatch init`, `doctor`, `scan`, and `check`. The timer runs `scan` with the configured profile's `HERMES_HOME`, and `scan` takes the profile from the running Hermes, because Hermes consumes a `--profile` argument itself.
- `scan` sends the user line through Hermes' send path. A line is recorded only after it was delivered, and an unanswered or unsubscribed warning is checked on every scan.
- The checks read a card's exit code, outputs, fingerprint, basis, and reject count from run records and the live result, not from the card body.
- Optional `watch_hook` scan on the Kanban dispatch tick, off unless set.
- The gate blocks `kanban_complete` and `kanban_request_review` when a check fails. It approves only a result whose fingerprint, basis, and clean state match the recorded PASS as they are now, and it freezes exactly the fingerprint it checked.
- `examples/worker/run_executor.py` runs the executor in the foreground, records the run, and reads the review verdict from the review output. All paths in the record are absolute. A card behind an approved gate runs on its own work copy made from the approved snapshot, and is blocked when the gate has no snapshot. A review needs an output written by that run.
- `doctor` fails below the tested Hermes version and warns, without failing, above it.
- `scan`, `check`, the watch hook, the gate, and the card tools use the installed Hermes Kanban board.
- A passing gate approval writes the snapshot path onto the card.
- `taskwatch_create` and `taskwatch_reject` create cards and reject a gate. Create and reject run under the state lock, a failed create archives the children before their parents, and a reject writes its id and the card's last event id before it reopens so a retry finishes a half-done reject. The reject cap counts finished rejects, and a new reject id is refused while another is pending. A review-gate reject is refused, because Hermes has no public way to reopen the fixed worker card together with the review.
- `check --apply` and the apply examples stop when the fingerprint differs. The copy example publishes only a copy it hashed itself.
- Example skill telling a worker to run the executor in the foreground, to hand the verdict line to the review output, and to let the next card run on the approved snapshot.
- README install, update, and removal order, and docs for every config key, every check (what it blocks and when it can be removed), and the seven principles with their sources. Document approval trust boundaries, scan read failures, and known operational limitations.

### Changed

- Store current jobs as atomic checksummed per-job snapshots with durable receipt membership and recoverable compact watch events; migrate legacy ledgers once without dual-writing them, and conservatively replay older needs cursors ([Job records](docs/configuration.md#job-records)).
- `CONTRIBUTING.md` uses "must" only for what CI enforces and gives the commit and pull request format as the recommended form, without describing the runner's own checks.
- The distribution is renamed `agent-taskwatch`, and so are the systemd units (`agent-taskwatch-scan.service` and `.timer`) and the installed data path; the command and the import package stay `taskwatch`. An existing host reinstalls as `docs/configuration.md` says ("Reinstall after the rename").
- Code jobs that build a result no longer wait for each other on one target, since each has its own branch and worktree; the slot limit still applies, and non-code and review-only jobs on one target still wait.
- Docs describe the standalone job runner only: README, `docs/checks.md`, `docs/configuration.md`, principles, contributing notes, and the package description no longer mention the removed plugin, cards, or gate, or call the project experimental.
- The plugin no longer changes environment variables, reads Hermes source, or writes the board database directly; profile and paths come from the plugin context and Hermes helpers.
- Generated timer units pin the configured profile with `-p`, and the apply example requires `HERMES_PROFILE`.
- `plugin.yaml` declares `taskwatch_approve`.
- `doctor` no longer checks review-gate reopen support or fails solely because that support is unavailable.
- The job field `kind` is now `review` with values `code`, `design`, and `source` (`document` and `research` merged into `source`), the reviewer launcher flag `--kind` is `--review`, the `review_command` placeholder `{kind}` is `{review}`, and `docs/review/source-checked-document.md` is `docs/review/source.md`; old `jobs.jsonl` records with `kind` still load.

### Removed

- `taskwatch watch <job>`: use `taskwatch needs --wait --from <cursor>` instead (`docs/configuration.md`, "What needs the owner").
- The Hermes Kanban plugin: the plugin entry, cards, completion gate, Hermes tools, the `hermes taskwatch` command, their examples, and the shared-module code only they used. The `taskwatch` job runner is unchanged.

### Fixed

- A resumed RPC conversation is bound to the model its process launched with, not to the saved one: after a usage-limit failure the next launch of a command such as `omp --model @task` uses the current role order and the same conversation continues. A `public_text` base outside the unit heads is stored as its submit-time commit SHA, so moving that ref no longer makes a reviewed result stale (`docs/configuration.md`, "Model selection" and "Submit an approved job").
- Job state validates checksums, preserves torn tails and refuses conflicting receipt identities; see [Job records](docs/configuration.md#job-records).
- The delivery card is written in the configured `language`: `WORKFLOW.md` tells the worker to write the `Card` lines in it and the review prompt tells the reviewer to write finding `summary` and `not_checked` items in it. Without the key, the language of the intent stays (`docs/configuration.md`, "Language"; `docs/kinds/brief.md`).
- The wake that starts the next stage sets the timer accuracy to 1 s (`--timer-property=AccuracySec=1s`); systemd's default of 1 minute let the next stage start 20 to 52 s late.
- A dead step on a full disk no longer burns three relaunches. If the job folder's or `TMPDIR`'s filesystem has under 256 MiB free, the scan parks the job as `user_wait` with reason `disk_full`, the path and the free bytes in `error`, and uses no recovery. Test runs also leave no read-only snapshot folders in the pytest base temp.
- A job with `approval_required` and `predecessors` asked the owner before its predecessors finished. It now stays queued until every predecessor is `done`.
- Verify declared output contents, including Git-ignored files, against PASS before delivery, and send stop notices without holding the global state lock.
- Send one stop notice per wait entry and recheck accepted PASS fingerprints before result delivery.
- Clarify safe plugin updates, default-profile timer pinning, production destinations, review executor responsibility, and user escalation; consolidate operational guidance.
- The enabled dispatch watch hook reports unreadable board evidence through the same user notification path as `scan`, without leaking the read error.
- P0 is only a rule break about runtime behavior or data. Style and wording are P2.
- The guideline check follows angle-bracket and reference-style local links.
- The scorer fails when an answers or mappings directory is missing or has no cases.
